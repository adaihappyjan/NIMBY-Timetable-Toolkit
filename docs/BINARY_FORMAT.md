## 1. 文件外层结构
```
[固定头 1380 B] + [zstd 帧（标准 zstd，magic 28 b5 2f fd）]
```
- 头以 ASCII `NMBY` 开头，随后 `02 00 01 00`（格式主/次版本）、`13 00 0a 00`。
- 头中包含若干 32-bit LE 计数、**两段 32 字节的类哈希/GUID 块**、以及以 `Das Rails\0…` 开头的**存档名（定长字段 + 大片保留 0 区）**。
- 头**尾部 4 字节 `0c 3f 1e 01` = 0x011E3F0C = 18,759,436 = 解压后大小**（size 提示）。
- 解压后熵 ≈ 5.26 bit/byte；`0x80` 占 26%、`0x00` 占 14% —— 典型的 **varint（LEB128）续位字节**海量出现，说明 payload 是**类 protobuf 的变长整数对象流**。

### 权威长度来自 zstd 帧，不是头
工具箱现有写入管线 `write_output()` 只做 `header + zstd(raw_after)`，**头原样不动**。而已验证的“车库接班”补丁会给 payload 追加字节（长度变化），游戏仍能正常读取。
➡ 结论：游戏加载时用的是 **zstd 帧自带的 content size**，头里的 size 字段只是过时提示。**因此变长编辑是安全的**，无需重算头中的哈希/计数（现有 garage-join 写入即活证据）。

## 2. 对象 id 编码与类型码（核心发现）
- id 在流中编码为 `uvarint(int(id,16) * 2)`（末位恒为偶，用于区分“这是一个 id”）。
- **id 的最高十六进制位 = 对象类型码**：

| type (id>>48) | 类别 | 导出JSON含? | 该存档数量级 | 说明 |
|---|---|---|---|---|
| `0x1` | **Track 轨道段** | 仅被引用 | 151k refs | 铁路几何主干，被线路/站台大量引用 |
| `0x2` | **Station 车站** | ✅ | 411 defs / 913k refs | 定位实体（2×f64 Mercator） |
| `0x3` | **信号机/道岔节点（推测）** | ❌ | ~7,377 | 携带 Mercator 坐标，导出里没有 |
| `0x4` | **Line 线路** | ✅ | 51 | code/color/stops |
| `0x5` | **Train 列车** | ✅ | 393 | name/code/tags |
| `0x6` | **Schedule 时刻表** | ✅ | 70 | shifts/trains |
| `0x7` | **脚本扩展定义** | ❌ | 少 | 即 `GARAGE_JOIN_VECTOR`（旁为车号 MR-73 / TTC 00xx） |
| `0x8` | **扩展实例绑定** | ❌ | ~16k | 旁有字符串 `stm_timetable_garage_join_1` |

> `0x9–0xf` 在普查中出现但 id 非顺序（如 0x96cf607fffff3），是几何数据里的**假阳性**（巧合的 varint 串），非真实对象类型。

**意义**：信号机、道岔、完整轨道几何**只存在于二进制**，导出 JSON 完全不含。这正是“复刻现实路网 / #10 二进制编辑”的真正瓶颈所在。

## 3. 记录布局（已反解）

### 3.1 Station 记录
```
… [uvarint id] … [f64 merc_x] [f64 merc_y] [uvarint namelen] [name utf8]
   [00 00 00] [uvarint 区数/长度] [ 站台Track列表: uvarint track_id … ]
   [f32 from_t][f32 to_t] …
```
实测 “Toronto Union Station” 名前 16 字节 = 两个 float64：
- `x = -8,836,575.82`，`y = 5,410,593.43`
- 名字后紧跟其站台轨道 id `0x1000000000001`(10W)、`0x1000000010001`(10E)——与 Line.stops 里的 track_id 完全一致。
- 站台 `from_t/to_t` 为 **f32**（如 `00 00 80 3f`=1.0，`43 16 b2 3e`≈0.3479）。

### 3.2 坐标投影 = 标准 Web Mercator（EPSG:3857），R=6378137，**误差 0**
```
x = R * radians(lon)
y = R * ln(tan(pi/4 + radians(lat)/2))         # 反解:
lon = degrees(x / R)
lat = degrees(2*atan(exp(y / R)) - pi/2)
```
6 个车站反解与导出经纬度**逐位一致**（R_impl=6378137.000，误差 0.00e-6）。
➡ 任意真实经纬度都能**精确**换算成游戏内部坐标——可用于把真实站点逐字节注入/对齐。

### 3.3 Line / Stop（来自导出，物理布局与站点一致）
`Line{ id,name,code,color(0xAABBGGRR ABGR),tags,stops[] }`；
每个 `Stop{ idx, leg_distance(f32), station_id, arrival, departure, areas[[ {track_id, platform_name, from_t(f32), to_t(f32)} ]] }`。

### 3.4 脚本扩展（type 0x7/0x8）
`GARAGE_JOIN_VECTOR = 01 8280808080808007 dedceebcf08cfdee5b00008fd2e2ee97b1b4907d`
即“把某列车的 garage_join 扩展打开”的尾部向量；工具箱已能安全批量写入/移除（末尾定长向量替换 + 反向解压校验）。

## 5. 可安全编辑的字段（按风险从低到高）

| 编辑目标 | 位置 | 宽度 | 风险 | 方法 |
|---|---|---|---|---|
| **车站坐标对齐真实经纬度** | Station 名前 16 B | 定长 | 最低 | 就地覆盖 2×f64（长度不变，size/哈希都不受影响） |
| **线路颜色** | Line.color | 4 B | 低 | 就地覆盖（注意 ABGR 字节序） |
| **站台 from_t/to_t** | Stop.areas | 4 B f32 | 低 | 就地覆盖 |
| **车库接班扩展开关** | train 记录尾 | 定长向量 | 低（已验证） | 复用现有 `GARAGE_JOIN_VECTOR` 补丁 |
| **车站/线路改名** | 变长字符串 | 变长 | 中 | 需按现有 schedule 改名同款“定位+长度差补丁+反向解压校验” |
| **新增/删除 站/轨/信号** | 全流 | 变长+计数 | 高 | 需完整序列化器（会牵动 header 计数与海量引用），暂不建议 |

**统一安全护栏（沿用工具箱既有做法）**：
1. 只写新文件，绝不覆盖输入；`.partial` 原子落盘 + SHA256。
2. 写前用 id+name 唯一定位记录（多命中即拒写）。
3. 压缩后 `zstd 反向解压 == 期望 payload` 才落盘。
4. 全程基于 `_backups/` 副本验证，通过后再交给用户。

### 8.4 Line 的 stops 语法完全反解（本轮攻克）
- **关键结论**：线路的 name/code/color/**按序站点** 都存在**带名记录**上（该记录 id 末位为 `0x6`，即游戏内统一的 Line/Schedule 对象），`0x4` 记录不携带名字。
- 记录语法：`[id][namelen name][codelen code][tagcount=00][color uvarint][flags…][stopCount][每站块…]`；
  - `color` 为 uvarint，值即 `0xAABBGGRR`（ABGR）；例 `a9 81 80 f8 0f` → `0xFF0000A9`。

- **校验（对拹导出 JSON）**：站序 **35/37 完全一致**、颜色 **33/37 一致**（其余差异来自该存档与导出为不同游戏状态，站点数 166≠411 已佐证）。

### 8.6 车站记录两种变体 + 车队直读（本轮修复）
- **车站 id 恒在坐标对前 12 字节**：记录形如 `[id(0x2)][4B meta][f64 x][f64 y]…`。据此按“坐标 + 前 12B 的 id”枚举可得 **全部 411/411 车站 id 与坐标**（此前的“坐标后紧跟名字”启发式只覆盖 166）。
- **两种记录变体**：
  - 玩家命名的车站：坐标后**内联** `[namelen][name]`（166 个，名字 166/166 精确）。
  - 真实路网/Mod 导入的车站：坐标后是 `00 01 00 00 04 [站台轨道…]`，**存档内不含名字**（名字由 mod 提供，全档搜不到），读取时给出稳定回退标签 `车站 0x…`。
- **意义**：坐标级对齐现覆盖全部车站（按 id 定位，与名字无关）；坐标 411/411 精确。
- **Train 车队直读**：`[id(0x5)][meta][namelen][name]` 自描述枚举，真实存档 **393/393** 精确命中。

### 8.8 Schedule(0x6)时刻表容器直读 + 两种记录变体（本轮）
- **记录布局**：`[id(0x6)][name][str2][str3][color varint(ABGR)]…`，color 解出与导出 `0xff0000a9` 完全一致。
- **两种 id→name 变体**：
  - 变体 A：`[id][namelen][name]`（多数对象）。
  - 变体 B：`[id][额外 uvarint 字段][namelen][name]`（部分 schedule，如 `REM/STM/EXO … Daily`）。
  - 统一用“id 后可跳过 0~2 个前导 uvarint 再读名”的容错读取，两类全覆盖。
- **通用 id 守卫**：真实对象 id 结构为 `type<<48 | major_index<<16 | 小子索引`，实测所有类的低 16 位 ≤0x8；因此对 `_is_id` 加 `低16位 ≤0x100` 守卫，一次性过滤所有读取器的噪声误配（本例过滤掉 1 条假 schedule）。
- **验证**：真实存档 **schedule 70/70**（id 全中、名字全中）；带几何(≥2 站)的路线 37 条，站序 35/37 精确（与历史基线一致，无回归）。
- **意义**：`network-read` 总览新增“时刻表 70”；同时**补齐了此前漏画的 2 条真实路线**（变体 B 之前读不到）。
- **顺带修正对象模型认识**：工具的“线路图”实际读取的是 **0x6 Schedule 内嵌的路线模板**（游戏里 Schedule 承载 name/code/color/站序），并非 0x4 Line（0x4 仅是一张线路 id 索引表）。

### 8.7 时刻表为“规则驱动”，具体到发时刻不入档（关键结论）
- 导出 JSON 里每条 run 的 `arrival_departure=[…秒…]`（**绝对**周内秒）在存档二进制中**搜不到**（uvarint/delta/f32 均无）。实测某班次每 7200s 发一班、一周正好 84 班——存档只存**规则**（线路每站相对时刻模板 + 班次发车规律），**导出时由游戏展开**成具体 run。
- **修正（见 8.11）**：绝对 run 时刻确实不入档，但**线路模板的“每站相对到/离时刻”是入档的**（此前误以为要靠物理仿真才能得到）。因此 `arrival_departure` = 班次发车基准（规则）+ 模板相对时刻（入档），二者相加即可复现，无需物理引擎。
- 线路的**发车频率/时段设置**位于 **~3.78M 线路运行图区**（含时段名“默认”与时间值，如 `c0 d1 02`=43200=12h；不同线数值不同）。这是“自动化时刻表”应编辑的字段，也是展开模拟器的输入。
- 推论：要让“时段/班距/覆盖”等 KPI 也脱离 JSON，需**复刻游戏的时刻表展开**；而“自动化时刻表”可通过**编辑频率字段**实现（只新档 + 反向解压校验）。

### 8.9 列车↔时刻表分配 + 时段/频率结构（本轮）
- **配置区**（~3.78M）：先是一段“schedule id 索引数组”（连续 8 字节 0x6 id、无数据），随后是每张时刻表的**配置块**：
  `[schedule_id(0x6)][name][code][color][flags][line_id(0x4) 引用][时段…][尾部分配对]`。
- **分配对（自校验）**：配置块尾部为 `[N][N 班次id×2 的 uvarint][N][N 列车 0x5 id]`，两侧计数相同。
  - 据此重建“每张时刻表 → 已分配列车集合 + 班次集合 + 班次数”。真实存档 **35/35** 集合与计数全部精确（0 漏 0 误）。
  - 注意：**列车↔班次的 1:1 配对不在此按位置对应**（两列各自按 id 排序）。真实配对按“创建顺序”，可由 ~3.66M 的**班次记录内嵌的列车 name/code** 反查（shift.name/code == 被分配列车的 name/code，实测 GO 008/1008 等一一对应）。
- **时段（band）结构**：配置块含一个时段，默认名“默认”，其后字段为 `[01][时长][02][00][V2][line_id]…`。
  - **时长字段取值仅三种预设**：43200(12h, 51 张) / 3600(1h, 18 张) / 7200(2h, 1 张)。
  - 而导出的**真实班距**（相邻 run 起点间隔）为 630/700/945/1800/7200… **高度分散**，与时长预设不对应。
- **结论（重要）**：**班距（发车间隔）不是直接存储的字段**，而是由“**分配的列车数 × 线路循环时间 × 时段窗口**”**规则推导**；具体 run 时刻同样只在导出时展开（见 8.7）。
  - 因此“**精确改班距**”无法通过改写单一字段安全实现；可安全调节的杠杆是：**分配的列车数**（已由“车库接班/批量绑定”支持）与**时段窗口**（单一 uvarint，可只新档+反向解压校验地编辑）。
  - 由此，KPI“去 JSON”应走：分配（车/班次数，已可）+ 线路循环时间（待解每站相对时刻）+ 时段窗口 → 估算，而非声称精确复刻导出时刻。

### 8.10 班距 = 循环时间 ÷ 车数（已实测验证）
- 用导出核对：定义单车循环时间 `T`=班次内相邻 run 起点间隔的中位数，线路班距 `h`=当日各班次首 run 起点排序后的相邻间隔中位数。
- 实测 **35/35** 张有服务的时刻表严格满足 **`h = T / N`**（`(T/N)/h = 1.00`），即 **`T = h × N` 是与车数无关的线路常量**。
- 应用（安全自动化，见“班距规划器”）：给定目标班距 `h*`，所需车数 `N* = round(T / h*) = round(h × N / h*)`。这让“目标班距→车数”可在**不写存档**的前提下精确给出增减建议；真正改变班距 = 在游戏内加/减车（贴合游戏机制、零坏档风险）。

### 8.11 逐站相对时刻**入档**（重大发现，实测精确到秒）
> 研究脚本：`_research/template_time.py`。此发现**修正了 8.7** 的“时刻不入档”的过度结论。

- **编码**：在 ~3.54M 的**线路路径模板区**，每个停靠点记录为
  `… <停靠序号=2k> 01 <进站行驶时间×2> <累计到达时刻×2> <累计离站时刻×2> …`，
  所有时间以 **0.5 秒为单位**（即数值 = 秒×2）。停站时长 = 离-到（实测常见 40s→存 80）。
- **计时挂在“路线对象”，不在“服务对象”**（关键澄清）：0x6 有两类——
  - **路线对象**（`TTC Yonge–University`、`STM Orange Line`、`GO Kitchener Line`…）：带**站序 + 逐站计时模板**。
  - **服务对象**（`TTC Line 1 Daily`、`STM Line 2 Daily`…，`stop_count=0`）：引用路线，承载班次/车队/时段（见 8.9）。
  - 因此**地铁线的逐站时刻同样入档**——只是挂在其路线对象上（起初误在服务对象上找，才误判“地铁无模板”）。
- **验证**：`模板值 ÷ 2` 与导出 run 的**逐站相对到/离时刻逐一相等**。真实存档 **32/37 条路线“整条模板逐站精确 + 循环时间 T 精确到秒”**（含大部分地铁线）：
  - **地铁/通勤**：TTC Bloor–Danforth 60/60、STM Orange 60/60、STM Green 52/52、TTC Eglinton 46/46、REM A1/A4 36/36、OT Confederation 34/34、TTC Finch West 34/34、EXO Vaudreuil 34/34、STM Blue 22/22、TTC Sheppard 8/8、STM Yellow 4/4…
  - **区域/城际**：全 8 条 VIA（20975/24099/28093/28485…）、GO Kitchener 24/24(10477)、Barrie 18/18(10033)、Milton 16/16(4849)、Richmond Hill 12/12(4089)、Lakeshore East 18/18(5343)、UPX 8/8(2477)…
  - 其余 5 条 `??` 为**导出侧命名/变体对不上**（如 Lakeshore West 主线喂两个服务、EXO Weekday 导出仅 1 站），**非提取失败**。
- **稳健化要点**（已修）：用**该路线自身第一处出现**（`read_lines` 取站序的同一区）+ **按已知站数限定走查步数**，杜绝“取最长走查”误穿入相邻线模板（此前 GO Barrie/Milton 等都误得 VIA 的 20975）。
- **循环时间语义**：模板 T = **单程一趟运行时长**（行驶 + 停站）；而“每车发车间隔”还要**加折返/停留**（如 Kitchener 模板 T=10477 vs 按 8.10 的 h×N≈10800，差 ~323s 折返）。故 T 可直读，但与“班距用的循环时间”差一个折返量。
- **已产品化**（本轮）：`toolkit_savereader.read_line_timetables(raw)` → 每条路线 `{id,name,color,cycle_seconds,stops:[{station_id,arrival,departure}]}`；后端命令 `line-timetable`；总览路线行显示**循环时间**；新增 Web 面板“**逐站时刻表直读**”。单测 `test_read_line_timetables_relative_times`。**只读**，不写存档。

### 8.14 发车基准 / 折返 / 班距 —— “最后一环”结论（本轮攻关）
目标是让“体检运营 KPI（班距/服务时段/覆盖天数/发车时刻）”也能仅凭存档运行。结论如下，全部用真实主存档 `Das Rails.nimbyrails5` + 导出真值逐项对账。

- **发车基准秒 / 逐 run 发车序列：不入档。** 全局搜过各 run 起点（如 GO Kitchener 首班 7160）与 run 间隔（10800）的 varint（含 ×2），命中**全部落在 Track 几何的 float64 内**（如 `…b0 54 41…` 属浮点尾数），无独立字段。导出里每班次 56 个 run 起点是**游戏运行时按规则展开**的结果，存档只存**规则**（时段 band + 分配车数 + 模板），不存展开后的时刻。
- **时段(band)结构：** 配置区（~3.78M）每张时刻表块为 `name → code → color(ABGR,已用 0xff3fb927 反证) → flags → line_id(0x4) → 车数N → … → band`；band 内含 `06 <big-varint> <window>`。真实存档扫描：**window 绝大多数是默认 3600**，且 anchor 会误命中噪声（如 GO Barrie 得到 8162）。**语义不稳、且导出里 Schedule 根本不含 band 字段**（导出 Schedule 只有 color/id/name/tz/tags/trains/shifts），无法用导出校验。故**不做 band 写入**——遵守“多命中/未命中一律拒写”铁律。
- **班距 = 派生量，可高精度估算。** 精确关系 `h = 循环间隔 / N`，循环间隔 = 模板 T（已直读，8.11）+ 折返/层停。折返不单独入档但很小（Kitchener 323s、STM Green 81s、TTC BD 77s…），故 **`h_est = T / N` 系统性略偏小**。实测 36 条线：**中位误差 3.5%、均值受个别重复“Daily”变体拉高、within 10% = 26/36、within 5% = 22/36**；在“T、N 均干净直读”的 16 条主线上，`ops-analyze` 对账**中位误差 4.6%、within 10% = 11/16**。
- **落地：** 新增后端命令 `ops-analyze`（纯存档直读估算 `h≈T/N`；可选 `--export` 作**只读真值护栏**逐条对账并给命中率；可选 `--target-headway` 给出“目标班距→所需车数”规划）。纯函数 `estimate_headway / plan_train_count / export_service_kpis` 有单测；Web“总览与体检”页新增“**仅用存档估算运营指标**”面板。所有值明确标注 `method=estimate`，绝不谎称精确。
- **写入侧诚实结论：** 由于班距不入档、band 语义不稳、直接改分配车数需连带重写班次/车绑定（结构风险高），**目前不存在“单字段安全改班距/车数”的可写杠杆**；因此自动化时刻表**只交付精确的“目标班距→车数”规划**，写入仍走既有、已测的**安全通道**（`extension` 车库接班 / `fix-tasks` / `repair`，全部 `write_output`：只新建存档 + 反向解压校验 + 原子落盘 + 拒改原档）。宁可不写，也不违反安全铁律。

### 8.15 Track 轨道几何直读（本轮攻克，只读）
导出 JSON **完全不含**轨道几何——它是“复刻现实路网”最有价值、也最大的一块（占文件绝大部分）。本轮把它做到**可绘制直读**：

- **对象形态：** 每个 Track（id 高 nibble `0x1`）是被网络绘制所用的**图节点**：一个 Web Mercator 坐标（与车站同投影，2×float64）、小头 `[00 <邻居数≤12> 00 …]`、若干**邻居 Track id**（邻接关系），以及它接触的 Station(0x2)/Signal(0x3) 链接。
- **读取算法（`read_track_geometry`）：** 用“第 8 字节 == 0x1”的快速前置过滤扫记录起点 → 建 `major_index → (lon,lat)` 映射与邻接表 → 对每条“两端坐标均已知”的邻居画一条边；用车站包围盒（±40 km）夹坐标、丢弃 >2 km 与 <1 m 的退化段（真实相邻节点相距数十米，实测中位 ~90 m）。**纯只读**，产出节点点 + 可绘折线段 + 总里程。
- **主存档实测：** 21214 节点 / 14539 段 / **3304 km**，坐标范围 lon −83..−63、lat 42.3..48.6（多伦多↔蒙特利尔↔魁北克/海洋省），首段落在多伦多 Union 一带——与真实路网吻合。
- **落地：** 后端命令 `track-geometry`（`--save`，返回节点数/段数/总公里/`segments`）；“现实路网参考图”页新增“**显示真实轨道**”开关与“直读真实轨道几何”按钮，用 Leaflet **canvas 渲染器**叠加约 1.5 万段折线（SVG 会卡），呈现真实轨道走向（曲线折线，非站点直连）。合成样本单测覆盖 A-B-C 三节点建图。
- **仍未解（且缺真值）：** Track 记录在 coord(f64×2) 之后为 `[f32×2(实测多为 0.0/0.5)][站台 0x2 链接][flags/零][信号 0x3 链接…]`；逐段**限速 / 电气化 / 轨距 / 样条控制点**多为默认零值。**关键阻塞：导出 JSON 完全不含任何 Track 字段**，因此这些标量**没有任何真值可对账**——无真值的逆向只能靠猜、极易输出错误数据，违背“多命中/未验证一律不产出”的铁律。故几何（坐标已用范围 + 真实路网吻合校验）为安全交付，逐段标量字段在获得可信真值前**不做解读、不产出**。
- **run 数/发车不入档（再次证实）：** 顺带排查了 run 区（~4.13–4.25M），其记录为**每辆车的 train-slot / motion 绑定**（含 0x5 train id、状态标志、时间戳大 varint），**不含**“每班 run 数”这类计数——印证 §8.14：run 序列与发车时刻是运行时按规则展开、不入档。故“车库连续循环”的精确 run 计数 JSON-free 不可得，只能借 route↔service + 单站车库线做**结构性**提示。

### 8.16 route↔service 链接直读（本轮攻克，让“体检”去 JSON）
导出把“线路”拆成两类对象：**Line(0x4)** 51 个（物理线路，带站序/几何）与 **Schedule(0x6)** 70 个（时刻表容器，持有 `trains / shifts / runs`，每个 `run` 带 `line_id`(0x4) 指向所服务的物理线路）。二者**同名成对**（如 Line `0x4…30001` 与 Schedule `0x6…40001` 都叫 “GO Kitchener Line”）。此前“体检”要判断“某线是否有车/空跑”必须读导出的 `Schedule.trains` + `run.line_id`；本轮把这层链接从二进制直读出来。

- **入档形态：** 服务型 Schedule 的**配置块**（~3.78M 配置区）为 `id → name → code → color(ABGR) → 02 → line_id(0x4) → 每线 band 配置(含 43200s=12h 时段窗) → … → [N][N shift ids][N][N train 0x5 ids]`。`line_id` 即该时刻表所服务的物理线路；纯 route 模板（无 run）的块里没有这些 `02 line_id` 标记。
- **提取（`_line_ids_in` + `read_schedule_assignments.line_ids`）：** 复用已可靠定位的 assignment 锚点，在 `[schedule_head, train_run_start)` 窗口内收集 0x4 line id——与 assignment 同一次扫描完成，无跨块串味。
- **实测校验：** 对 35 个“有 run 的服务型时刻表”，与导出 `run.line_id` 集合对账 **34/35 精确 + 1 超集 + 0 错误**。route 模板（无 run）正确地不产出 line（其名与对应 Line 同名，无需再解 0x4 名字）。
- **落地：** `AssignmentRecord.line_ids` 携带所服务线路；`save-overview` 每行新增 `is_service / served_lines`，Web“总览”页据此把 35 张运营时刻表标“运营·N线”，并新增 **JSON-free 存档直读体检**（健康分 + 问题清单：重名时刻表、闲置列车、未读到循环、疑似空模板）。**诚实边界：** 纯存档模式下天然没有“JSON↔存档不一致”可查（存档即真值）；发车时刻/精确班距仍不入档（§8.14），只作估算。

### 8.17 自定义时刻表设计器（Timetable Studio）+ “写入自定义时刻表”可行性定论
本轮新增前端 **自定义时刻表设计器**（Web“时刻表配置”页顶部）：

- **输入（全部免 JSON）：** 复用 §8.11 的 `line-timetable` 逐站相对到发时刻（半秒单位，32/37 线精确到秒）+ 单程运行时间；用户设 首/末班、峰/平班距、高峰时段、终点折返、单/往返方向。
- **计算（客户端）：** 按时段生成发车序列 → 用逐站相对时刻传播出每车次的逐站绝对到发；往返用 §8.11 模板的**对称反向**构造回程；用“最早空闲车”仿真求**所需车数**。
- **产出：** ① **Marey 弦线运行图**（时间×车站，斜线=车次，峰段自动加密，SVG 可导出）② 逐站到发时刻板 ③ 指标（车数/日车次/班距/循环）④ **游戏内复刻清单** ⑤ CSV/JSON/SVG 导出。全部只读。

### 8.18 写入自定义时刻表：两次失败 → 受控 diff 定位真正的输入字段

本节记录一段完整的“假设—实验—证伪—再定位”过程。**前两次写入尝试都在游戏内失败了**，第三次靠**受控二进制 diff**拿到确定性答案。

**外部调研：**
- 存档＝自研 **serde v2**（版本化 visitor，见 devblog 2020-03）。社区只有读 JSON 导出的 [nimby2sql](https://github.com/rlvelte/nimby2sql)，**无任何写存档实现**。
- 头部含 game data 哈希，但**本地加载不校验**（既有坐标/迁移写入都原样保留头部且能进游戏）→ 对象流可自由改写，只要结构合法。
- wiki《Timetable》/《Simulation》：整张时刻表**在加载时（“initializing timetables”）重算**，且 “line timings 不入档，每次加载重新计算”。
- devblog 2022-08：线路真正保存的输入是**每站 min. stop value + 每段 leg speed**，由“run 起跑时间”推算实际时刻；wiki《Line》的 *Default timings* 面板含 参考列车 / 巡航速度 / 最大加速 / 最大制动 / **Default stop time**（“未手动修改时赋给每个停站的停站时间”）。

**失败尝试 ①：改累计 `arr/dep` 缓存。** 按 §8.11 的 `<idx=2k> 01 <leg*2> <arr*2> <dep*2>` 改写停站等待并级联，37/37 条线路通过字节级回环闸门，生成测试档。**游戏内无效**——停站仍≈35s。印证 wiki：该区是**加载时被重算覆盖的派生缓存**。

**失败尝试 ②：改每站 stop time 副本。** 用导出 `leg_distance` 做锚点，定位到 `leg_distance_f32_off + 16` 处一个**全档 51 线 / 962 站恒为 60**（半秒制＝30s）的字节，改成 120（60s）。**游戏内仍无效**。

**受控 diff（决定性）：** 请玩家**全程暂停**下连存两档——`DIFF_A`（默认停站 30s）→ 仅把 *Default stop time* 改成 59s → `DIFF_B`。暂停使模拟状态不变，diff 于是只剩目标字段。结果在 `OT Airport Link` 记录内干净地暴露出结构：

```
每个停站   <leg_distance f32> <leg_speed f32> <accel f32> <brake f32> <stop_time uvarint>
线路默认   <cruise_speed f32> <accel f32>     <brake f32> <ref_train id 0x5> <stop_time uvarint>
```

- `accel/brake` 在“继承线路默认”的停站上为 `0.0`，正好对应 wiki 的 *Default timings* 面板。
- `stop_time` 为 **半秒制 uvarint**：ground truth 对里 5 个字段整齐地 `60`(30s) → `118`(59s)。
- **尝试②失败的原因由此确定：** wiki 说线路默认值“会赋给每个停站”，游戏**默认值与每站副本是一起写的**，加载时又用默认值刷回继承型停站——所以**只改每站副本会被静默还原**。必须**两者同写**。
- 附带确认 `arr/dep` 缓存确为派生：stop0 出发 `40`(64＝32s)→`7e`(126＝63s)，其后各站到发整体顺延。

**落地（`toolkit_timetable_writer.py` + 后端 `timetable-write`）：**
- `find_line_timings()` 按上述签名**免 JSON**定位每线的每站 stop_time 与线路默认 stop_time；`_find_default_stop_time()` 以**参考列车 id(0x5)** 为锚。
- **正确性闸门** `stop_time_roundtrip_identity()`：原值重编码后须与原 `raw` 逐字节相同（DIFF_A/DIFF_B 各 38 线，**失败 0**）。
- `set_line_stop_time()` 同时改写**线路默认 + 全部每站副本**，复刻游戏自身写法。
- **离线最强证明：** 让写入器把 `DIFF_A`(30s) 改成 59s，产出的 stop_time 字段与**游戏自己存的 `DIFF_B` 完全一致**（`[118]*5`），其它线路连带改动 **0**，文件长度不变。
- **只新档 + 多重校验：** 回环闸门 → 改写 → 重解析（全部字段须等于目标半秒值）→ 全线路连带零变化 → 压缩后 read-back。

**交叉校验与已知边界：** 严格定位器在全档得到 920 个 stop_time 字段（913 个为 60），17 条线路数量与站数精确吻合，20 条偏少（多为 GO 线，少 3 个）——推测是 `station_id = 0x0` 的**航点(waypoint)**结构不同（nimby2sql 亦专门过滤此类）。因此写入器在**找不到线路级默认字段时直接拒绝写入**。

**发车间隔/时段窗口**这类无真值字段仍**不写**（§8.9/8.16 铁律不变）。

### 8.19 逐站停站时间：破解每站“手动修改”标志位

§8.18 只能整线统一改停站时间（写线路默认 + 全部每站副本）。要做**逐站不同**，需要每站的“手动覆盖”标志。再次用受控 diff 拿下：

**受控实验：** `FLAG_A`（全线默认 45s，全部继承）→ 仅把**第 2 个停站**设为自定义 59s → `FLAG_B`（全程暂停）。diff 只在该站暴露两处变化，从而解出每站的完整结构：

```
每站   <leg_distance f32> <leg_speed f32> <mode 8 字节> <stop_time uvarint>
   继承站  mode = 00 00 00 00 00 00 00 00
   手动站  mode = 00 00 00 80 3f 00 00 02   （mode[1:5]=f32 1.0，mode[7]=0x02）
```

- 继承站：加载时被线路默认值刷回（§8.18）。手动站：`stop_time` 独立存活，不受默认值影响。
- `FLAG_B` 仅第 2 站变手动（mode 置位、值 118=59s），其余继承、默认值 45s 未动——干净单点。

**落地（`toolkit_timetable_writer.py`）：**
- `_find_stop_time_fields` 升级为同时识别继承站（mode 全 0）与手动站（mode[1:5]=1.0），`StopTimeField` 记录 `mode_off / is_manual`。
- `set_stop_times(raw, line, [秒 或 None], default_seconds=None)`：对给值的站写“手动模板 + 值”，对 `None` 的站写“继承模板 + 默认值”；带回环闸门。
- **离线最强证明：** 让它把 `FLAG_A` 第 2 站改成 59s，产出的 **mode 区与 stop_time 与游戏自存的 `FLAG_B` 逐字段一致**（`000000803f000002`/118），其它线路连带 0。
- **游戏内验证通过：** `Das Rails PERSTOP TEST` 把 OT Airport Link 四站设为 15/30/45/59s，进游戏逐站显示各不相同、与设定吻合。

**后端/前端：** `timetable-write` 新增 `--dwell-list`（逐站秒数，逗号分隔，留空/`-`/`*`=继承）；Web“时刻表工作室 → 停站时间写入”新增“整线统一 / 逐站设置”切换，逐站模式按线路停站列出可逐格填写（占位显示当前继承值），一键“全部清空/全部填默认”。仍只写新档、带回环+零波及+压缩回读三校验。

### 8.20 车站名称写入：把“模组编号站”改成真实站名（本轮攻克，可写）

游戏里由现实路网模组生成的车站显示为 id 编号（如 `车站 0x2000000370001`），
其“真实名称”（模组名称，如 *Barrie South GO Platform 6*）只存在于导出/模组，
不落在存档里。本轮把车站名槽位彻底解出，可**一键写回真实站名**。

- **入档形态**：车站记录 `… [f64 x][f64 y] <namelen uvarint> <utf8 name> <flag> <b1> <b2> <plat_count> <平台 track id…>`。
  - `flag = 0x00` → 玩家自定义名（游戏显示该 name）；`flag = 0x01` → 继承模组/自动名（游戏显示编号）。
  - 未命名站为 `namelen=0` + `flag=0x01`；`b1/b2` 与平台结构原样跟随，改名时**完全不动**。
- **实测校验**：主存档 411 站逐站回环——重编码原槽位与原字节逐位一致；名称即写在坐标之后。
- **写法（`toolkit_coordedit.set_station_names`）**：仅重写 `<namelen><name><flag>` 这一段（变长），
  写入 UTF-8 名 + 强制 `flag=0x00`，其余字节不变；用 `_apply_spans` 变长拼接（对象 id 按序号
  非按偏移，移位安全）。名称来源=导出 JSON 的 `Station.id→name`（`station_names_from_export`，
  流式扫描，不整体 json.load）。
- **安全**：只新档；写前逐槽位回环校验，写后**重解析确认每个目标站读回目标名**，再压缩+反向解压回读。
  默认只补写未命名站（`--all` 才覆盖已命名）。实测 245 站写入 / 166 已命名跳过 / 文件 +2513B / 校验通过。
- **后端/前端**：命令 `station-name-write --save --output --export [--pair id=名 --all]`；
  首页新增“真实站名写入”面板，一键从导出补写真实站名。**游戏内是否显示仍需玩家读档验证**（机制与
  玩家手动改名一致，置信高，但遵循“先出测试档、玩家确认”铁律）。

### 8.21 每段限速(leg speed)/重叠距离：受控档不可净 diff（本轮结论）

玩家提供的 A（限速 60/重叠 4m）↔ B（限速 180/重叠 10m）**无法净 diff**，原因：
- **未暂停**：两档差 ~49KB，含 motion/epoch 等无关抖动。
- **重叠距离会重新细分轨道几何**：改 4m→10m 令 Track(0x1) 节点/段数变化，
  自 ~1.05M 起整段对象流**错位**，逐字节 diff 从此失效（[0..1.049M] 基本一致，之后 40%→95% 全差）。
- **两变量同时改**：限速与重叠纠缠，即便对齐也难归因。
- 时刻表模板里的 `leg_speed`（8.18 的 `leg_distance` 后那个 f32）实测值域 ~2.5–3.1，**并非**面板 km/h 限速；
  真正的“轨道限速”是 Track(0x1) 逐段属性（§8.15 已列为未解降级项）。
- **结论**：要破解轨道限速，需**暂停**下、**只改限速一项**（不动重叠、不重绘轨道）的 A/B 对，
  使节点数不变、对象流保持对齐。重叠距离因天然改几何，需另设专门实验。

### 8.22 时刻表运营规则（BAND_A/B 决定性修正）

**再次修正旧推断**：配置块里名为 `默认` 的对象不是“窗口长度 band”，而是时刻表的**指令列表
（Order List）**。它后面先保存逐条运行指令，再保存 10 个偏移组的分布策略。
此前把 `3600+39600=43200` 解释为两个窗口相加 12 小时属于巧合；真正的数值全部使用游戏通用的
**半秒制（实际秒 ×2）**。后续 `BAND_A → BAND_B` 受控实验给出了逐字段真值：目标表
`OT Line 4 Daily`，线路 `OT Airport Link`；入库 `00:30→01:00`，出库 `05:30→08:00`，
仅把出库改为工作日，并把偏移改为固定 7 分钟。

配置结构（省略不变元数据）：

```
<Schedule id> ... 06 "默认" <顶层指令数 N>
  N × [
    <时刻秒×2> <日期掩码×2> <偏移组索引×2> <Order id> <Line(0x4) id>
    <重复参数> <继续下一指令> <计时事件> <进入站选择>
    <退出站选择> <计时站选择> <跨圈偏置> <堆积子指令数 M>
    M × [<一条完整指令记录；其自身堆积数必须为 0>]
  ]
  10 × [<分布模式×2> <固定间隔秒×2> <手动总时长秒×2> <时长来源 Line id>]
```

这些字段都是 **uvarint**，不能当成固定 8 字节切片；数值较大时会占两字节以上。聊天记录里写成
`<flag2> 1 2 <X> <X> 1 0 0` 的正是 8 个**单条指令参数**，不是班距：

| 参数位置 | 常见值 | 语义与证据 |
|---:|---:|---|
| 0（旧 flag2） | `00` / `02` | **重复**：`00`=Max/∞，`02`=x1；由历史存档与界面 x1/∞ 对照确定 |
| 1 | `01` / `00` | **继续下一指令**：`01`=开，`00`=关；由 `PARAM_CONT_ON_A/OFF_B` 单变量存档确定 |
| 2 | `00` / `02` / `04` | Timing event：准确到达 / 准确发车 / 不迟于此时到达 |
| 3（旧 X1） | `01` 或多字节值 | **Enter 选择器/id**；不是班距 |
| 4（旧 X2） | `01` 或多字节值 | **Exit 选择器/id**；不是频率 |
| 5 | `01` | Timing 站选择器，当前为 `<Same as enter stop>` |
| 6 | `00` | Timing loop bias，当前为 `=`（同一圈） |
| 7 | `00` / `01` / `02`… | **直接堆积子指令数**；子指令是紧随父项的完整记录，且不计入顶层 N |

`PARAM_GROUP2_C` 还锁定了偏移组的真正位置：它是**日期掩码之后、Order id 之前**的独立
uvarint；组 1=`00`、组 2=`02`。该实验只把这一处由 `00` 改为 `02`，后面的 8 个指令参数完全不变。

当前截图中的 `OT Confederation Line` 指令直接给出了聊天记录里的两个 X：

```
00 01 02 d4 18 d4 18 01 00 00
```

按 8 个 uvarint 解码为 `[0, 1, 2, 3156, 3156, 1, 0, 0]`；因此
`X1=X2=3156`（原始编码均为 `d4 18`），是 Enter/Exit 选择值。`BAND_B` 的
`OT Airport Link` 使用默认首/末站选择，参数为 `00 01 02 01 01 01 00 00`。

后续单变量档 `TIMING_ARRIVE_EXACT` 将参数 2 从 `02` 改为 `00`，游戏回读为“以下时间准确到达”；
游戏 UI 与保存值还确认 `04` 为“不迟于以下时间到达”。三个站点选择器都使用线路内部的本地偶数 id，
`1` 是各自的哨兵：Enter=线路起点、Exit=线路终点、Timing=与进入站相同。每个 route Schedule
另存一张 `<站数 N> + N×[<selector id><线路站序×2>]` 表；站序值恰为
`0,2,…,2(N-1)` 的排列。真实 `ORDER_STACK_D` 中 51/51 条 Line 的表均可完整读出。线路改动时，
不属于新线路的 selector 自动回到 `1`；线路未改时允许原样保留存档中的旧 selector。

`ORDER_BASE_A → ORDER_INSERT_B` 证明插入不是引用另一种对象：顶层计数 `2→3`，新增的是一条
完整 24 字节（该样本长度）的变长记录，Order ID 取全局分配器的下一个偶数值 `7834→7836`，
根对象 `buildings` 前的分配器字段同步更新。`ORDER_STACK_C/D` 则证明“堆积”不增加顶层计数：
父项参数 7 依次 `0→1→2`，其后分别追加完整子记录 `7838`、`7840`，每个子项参数 7 为 0。

本机游戏程序的内置 UI 参数名进一步锁定了偏移组配置的后三项：

| 保存字段 | 游戏 UI 名 | 说明 |
|---|---|---|
| 模式 `00` | `Fixed interval` | 直接按固定间隔递增 |
| 模式 `02` | `Evenly over manual duration` | 在玩家输入的总时长内均分 |
| 模式 `04` | `Evenly over line duration` | 在所选线路运行时长内均分 |
| 数值 1 | `Interval` / `train_group_fixed_shift_by` | **固定间隔**，不是下限 |
| 数值 2 | `Duration` / `train_group_manual_duration_amount` | **手动均分总时长**，不是上限或频率 |
| Line id | `Duration of` / `train_group_line_duration_pick` | 按线路时长均分时使用的来源线路 |

不同模式的输入会同时留在存档中；未被当前模式使用的值不会自动等于 0。例如所有实档中的
`GO Lakeshore West Line` 为模式 `04`（按线路时长），但仍保留固定间隔字段 `3000s`、手动时长 `0s`。
因此旧解析器把两个数叫“偏移下限/上限”是错误的。

实档四处最小差异：

| 字段 | BAND_A | BAND_B | 解码 |
|---|---:|---:|---|
| 第 1 项时刻 | `3600` | `7200` | `00:30 → 01:00`（入库） |
| 第 2 项时刻 | `39600` | `57600` | `05:30 → 08:00`（出库） |
| 第 2 项日期 | `254` | `62` | `0x7f → 0x1f`（每天 → 周一至周五） |
| 组 1 分布配置 | `04 00 00` | `00 840 840` | 按线路时长均分 → 固定间隔；固定输入与手动时长输入均保存为 `840/2=420s=7min` |

- `BAND_B` 两条指令都在**偏移组 1**；车库指令参数首值 `02` 表示 x1，机场载客指令首值
  `00` 表示 Max/∞。旧结论把重复次数误写成偏移组，现已由界面与单变量存档推翻。
- 条目里的引用是**加倍编码的 Line(0x4) id**，不是此前误判的 0x8 对象。
- 日期掩码为常规位图：`0x7f`=周一至周日，`0x1f`=周一至周五；文件里仍以 `mask×2` 写入。
- 模式值同样按整数×2 保存：`0=固定间隔`、`2=按手动总时长均分`、`4=按线路时长均分`。
- `toolkit_scheduleconfig.py` 只接受上述精确签名，写前做原值回环，写后重解析目标组并对比所有其它组；
  后端仍只生成新存档，经过压缩反读、校验和与原子落盘。
- 用解析器在 BAND_A 内重放四项改动后，`OT Line 4 Daily` 配置块与游戏生成的 BAND_B **逐字节完全一致**。

### 8.23 自定义运营时刻表编辑器的写入边界

Web“时刻表配置”页已把 §8.22 的结构实现为可视化编辑器。可安全改写范围：

- 每条指令的 Line、Timing 事件、Enter/Exit/Timing 站点、时间（0.5 秒精度、允许次日时刻）、
  日期掩码、偏移组 1–10、重复 Max/x1–x100和“继续下一指令”；
