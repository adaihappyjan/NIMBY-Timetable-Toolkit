# 工具箱功能研究：减少重复操作与解释运行故障

研究日期：2026-09-07。本次查看正在运行的游戏和工具箱、现有源码、已保存文件及官方 NimbyScript 文档；未修改游戏配置或存档，未实现以下建议。

## 已确认的依据

- 游戏列车管理显示 393 列车，时刻表管理显示 19 张表。
- 最新本地自动存档 `Das Rails Autosave 1.nimbyrails5` 解析得到 70 个运营组，其中 51 个符合线路自身模板特征，另外 19 个为独立运营表，与游戏列表吻合。因此不能把内部 Schedule 对象总数直接叫做用户时刻表数量。这是本次保存文件解析结果，不代表读取了游戏内存。
- 游戏 REM A1/A4 Daily 有 16 列车；偏移组 1 按线路时长 1:40:48 均分，显示班距 0:06:18。指令页显示每天 00:30 车库 x1、05:30 客运 Max。这不是当前存在故障的证据，但说明目标班距、实际分配和出入库时间应放在一起展示。
- 当前安装目录可见 EXE、DLL 和 resources；未找到可直接审阅的游戏 C++ 源码。本次游戏行为依据是界面、官方 API 和已验证的存档结构，不能声称审查了整个游戏源码。
- `toolkit_scheduleconfig.set_operating_group` 已支持时间、星期、十个偏移组、重复、接续、线路和站点选择器，以及新增与重排指令。已入档指令删除、跨父项移动堆积子项仍被拒绝。
- `web/app.js::opruleAudit` 只查缺失字段、旧选择器以及同一时间的星期重叠；尚不等于接续可行性或物理进路冲突校验。
- 工具箱规则包当前仅有车库接班、到站追加停留、信号前限速。车库接班实际是 `ss.match_pos = false`，不创建轨道或回库班次。
- 现有 Accounting TSV 有 company/line/station/train 多种粒度及 daily/weekly/monthly 等周期；日记录包括 649 行线路、5441 行车站、5502 行列车。字段包含信号等待、晚点、满载发车、候车超时等。当前工具箱未发现对应数据导入实现。
- 该 TSV 是 8 月 21 日导出的历史资料，不可解释为 9 月 7 日当前实时状态。例：游戏日期 2027-12-06 的 TTC Bloor–Danforth 日记录中，`trains_signal_stop_time=103030.800000107`、`trains_departures=26399`。指标单位和事件口径需在游戏会计页核对，不能把全部 departures 当作始发趟数。

## 建议开发顺序

| 顺序 | 功能 | 用户能少做什么 | 实现基础与边界 |
|---|---|---|---|
| 1 | 线路工作页与全局搜索 | 选 REM 后，在一个页面看表、车队、车库、班距、问题和相关操作 | 现有 ID/关联读取可复用；区分线路模板、运营表、车库线路，保留高级结构视图 |
| 2 | 项目状态、草稿自动保存、逐步撤销 | 重启或切换表后恢复未写入方案，不再重新填写 | 草稿放用户配置目录，以存档指纹和对象 ID 关联；目前 OPR 是内存草稿，切换存档会清空 |
| 3 | 存档与导出智能配对 | 不再靠文件名和“最新”猜是否同源 | 显示来源、游戏时间、更新时间和核对结果；文件稳定后读取，写入前再次核对；不给不匹配的文件强行放行 |
| 4 | 批量运营预设 | 多线一起套用工作日/周末、首末班、回库、峰平谷规则 | 在现有字段写入器上生成预览；按对象 ID 映射，不复制原始字节块；一批修改输出一份存档 |
| 5 | 七天接续与回库检查 | 直接看到哪列车哪天赶不上下一班，以及缺多少时间 | 先做计划时间与位置接续；空驶最短时长未知时必须标记未知；不声称完整复刻游戏寻路与调度 |
| 6 | 共线段发车协调器 | REM 等支线一起计算相位，预览核心段实际发车序列 | 识别共同站序及方向，以共线入口为基准计入各支线运行时间；处理峰平谷切换和跨午夜 |
| 7 | 车库占用与出入库时间轴 | 看车库何时拥挤、哪些车辆没有回库计划 | 先让用户指定车库与容量；计划占用与实际占用分开；轨道拓扑不等于停车容量或有效进路 |
| 8 | 实际运营问题排行 | 先处理候车超时、频繁满载或信号等待严重的线路 | 使用现有 Accounting TSV；按相同周期/粒度/ID 比较，空值标未知，避免生命周期和日数据重复累计 |
| 9 | 只读调度诊断脚本 | 将“没有班次/等信号/等计划时间”转成可读记录 | 官方 Motion API 提供相关状态；日志按状态变化或阈值记录，不在高频事件里持续输出；实机验证后发布 |
| 10 | 模组安装与启用状态助手 | 从“导出 ZIP 后自己找目录”缩短成安装、检查依赖、列出待启用对象 | private mod 安装可做；任意扩展实例仍不能声称都能批量写入，受字段和结构验证范围限制 |
| 11 | 任务中心与增量读取 | 扫描过程可看到阶段、失败原因，并复用已读取的同一份存档 | 一个受控写入队列、并行只读任务、按指纹缓存；读取日志游标，避免每次轮询重读整份进度文件 |
| 12 | 修复前后验收 | 一次操作后看到哪些表/车/字段改变，下一次导出是否符合方案 | 复用输出清单、结构快照、反读验证；“写入成功”“游戏加载成功”“运行验证成功”分开显示 |

## 需要优先修正的易用性问题

1. 对象数口径：内部 70 个对象不应直接误导成游戏列表中的 70 张运营表。
2. 地图规划点使用 localStorage，但服务每次分配随机端口。浏览器存储按源隔离，下一次启动可能读不到上一次规划点；应迁移到后端项目配置，并提供旧数据导入。
3. 模拟运行图与实际记录要明确标识；当前前端“冲突检查通过”的含义应收窄，避免被理解为不存在轨道占用或调度问题。
4. 显示实际使用的偏移组；未使用组默认折叠，避免用户误以为它们的零间隔需要修复。
5. 将 Enter/Exit/Timing 等词改为“从哪站进入/在哪站结束/以哪站校时”，技术字段放展开项。
6. 同一对象所有操作共用选择状态，区分“候选结果”与“可以执行”，出错提示给出对象、步骤、原因和下一步。

## 技术验证要求

- 批量写入：用多个运营表的测试副本验证，检查所有非目标表快照及全局 ID 分配器；保持原文件不变。
- 共线相位：覆盖不同支线入口运行时间、同站名不同 ID、反方向、循环重复站、07:00/09:30 切换和跨午夜。
- 七天回库：覆盖跨日末班、周四至周五、周日至周一、空白区间与不可达车库。无足够数据的约束输出“未知”，不自动判为正常。
- 运营指标：不把满载发车比例解释为平均载客率；不把累计晚点当作每位乘客的延误；合计必须避免跨粒度重复计算。
- 性能：工作进程数按内存预算和文件大小限制；多核只用于可并行部分，不等于整个任务都能线性加速。

## 官方接口边界

官方 NimbyScript 文档确认：无通用文件 I/O、网络或线程；公开扩展对象由游戏 UI 启用，脚本不能自行创建/编辑/删除公开扩展配置。`Motion::Drive.waiting_signal_id`、班次状态和站点事件可用于诊断；日志每次游戏会话需要玩家手动启用，且有明显 CPU 成本。因此第一版诊断应使用短时、过滤、低频日志，不能承诺外部工具箱随时读取完整实时调度数据库。
